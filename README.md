# Locali E2E API Testing Engine (Go)

Высокопроизводительный движок End-to-End API тестирования для микросервисной экосистемы доставки **Locali**.

## 2. Ключевые возможности

1. **Мульти-сессии для 4 ролей**:
   - Одновременное хранение и автоматическая передача Bearer JWT токенов для **Клиента**, **Ресторана**, **Курьера** и **Директора**.
2. **Валидация State Machine**:
   - Гарантирует корректность цепочки статусов (`NEW` -> `COURIER_ASSIGNED` -> `PREPARING` -> `READY_FOR_PICKUP` -> `PICKED_UP` -> `DELIVERED`).
   - Блокирует любые нелегальные прыжки (например, из `NEW` сразу в `DELIVERED`).
3. **Изолированность (Fixtures & Teardown)**:
   - Каждый тест автоматически генерирует уникальных клиентов, рестораны и курьеров.
   - Очистка ресурсов после завершения через стек `t.Cleanup`.
4. **Конфигурируемость**:
   - Переменная `BASE_URL` позволяет направлять тесты как на живой бэкенд (`http://localhost:3000`), так и на стейджинг или встроенный мок.
   - Поддержка готовых токенов через `CLIENT_TOKEN`, `REST_TOKEN`, `COURIER_TOKEN`, `ADMIN_TOKEN`.

## 4. Аутентификация и верификация

Движок подключён к обновлённому контракту входа бэкенда Locali.

### 4.1 Как движок получает одноразовый код

`POST /api/clients/register` на стенде с `DEBUG=true` возвращает выданный OTP
прямо в теле ответа (`debugCode`, LOCALIAPP-2343). Движок берёт его оттуда —
прогоны идут без участия человека. Источники кода перебираются по порядку:

| # | Источник | Когда срабатывает |
|---|----------|-------------------|
| 1 | `debugCode` из ответа `register` | стенд запущен с `DEBUG=true` |
| 2 | `VERIFICATION_CODE` / `verifyCode` стенда | стенд принимает универсальный код |
| 3 | Фиксированный код тестового номера `+79999999999` → `9999` | `USE_TEST_PHONE=true` и `DEBUG=true` на бэкенде |
| 4 | Ручной ввод оператора в UI | код приходит только в SMS/Telegram |

На проде поля `debugCode` нет — там остаётся ручной ввод или готовые токены.

### 4.2 Что движок знает о политике OTP

- код живёт 5 минут, повторная отправка на тот же номер — не чаще раза в 60 секунд;
- 5 неверных вводов исчерпывают бюджет попыток, дальше `429`;
- израсходованный код повторно не принимается.

429 разбирается типизированно: `client.RetryAfter(err)` отдаёт паузу из
заголовка `Retry-After`, поля `retryAfter` или из текста сообщения. Фикстура с
закреплённым номером пережидает лимит вместо падения прогона; неверный код
никогда не ретраится вслепую, чтобы не сжигать бюджет попыток.

### 4.3 Типизированные ошибки API

Любой ответ со статусом ≥ 400 приходит как `*client.APIError` с разобранным
конвертом бэкенда (`description` / `code` / `error` / `fields` / `retryAfter`):

```go
_, err := engine.ClientAPI.Register(ctx, req)
if client.IsRateLimited(err) {
    time.Sleep(time.Duration(client.RetryAfter(err)) * time.Second)
}
if apiErr, ok := client.AsAPIError(err); ok && apiErr.Code == "COURIER_ONLY" {
    // ролевой гейт, а не бизнес-отказ
}
```

Проверки в сьютах опираются на статус и машинный код, а не на текст сообщения —
русские формулировки на бэкенде переписываются.

### 4.4 Проверка ролевых claims

`client.VerifyRole(token, "courier")` убеждается, что выданный токен несёт
claims своей роли (`isCourier` / `isRestaurant` / `isAdmin`, для клиента —
отсутствие флагов). Это ловит регрессию, при которой ручка логина продолжает
отвечать 200, но подписывает чужой набор claims: без этой проверки все
последующие RBAC-ассерты молча зеленеют. Фикстуры вызывают её после каждого входа.

### 4.5 Сьют `auth_otp`

Отдельный набор в UI и в `go test`:

| Проверка | Что подтверждает |
|----------|------------------|
| `otp_issued` | `register` выдаёт код и он читается из ответа |
| `otp_login` | вход по коду выдаёт корректный токен клиента |
| `otp_replay` | израсходованный код повторно не принимается |
| `otp_attempts` | перебор упирается в `429` |
| `otp_resend_limit` | повторная отправка внутри 60 секунд → `429` с `retryAfter` |
| `role_claims` | курьер, ресторан и админ получают свои claims |
| `auth_gates` | `401` без токена, `401` на битом токене, `403` между ролями |

Запуск: `go test ./tests/... -run Verification` или кнопкой в UI.

### 4.6 Секреты в логах

`HTTP_DEBUG=true` печатает тела запросов и ответов; пароли, токены и
`resetToken` заменяются на `***` (`pkg/client/redact.go`). Одноразовые коды
намеренно НЕ маскируются: на тест-стенде это одноразовое значение, и именно оно
делает упавший шаг входа диагностируемым.

### 4.7 Фикстуры под контракт регистрации

- **Телефоны.** Генерируются строго в форме `+7` + 10 цифр — то, что принимает
  `normalizePhoneNumber`. Раньше курьер и ресторан получали номер из 10 цифр
  (`+7922` + 6), нормализация возвращала `null`, и регистрация отклонялась ещё
  до обработчика. Зарезервированный тестовый номер никогда не генерируется
  случайно.
- **Курьер.** Фамилия уходит в поле `surname` (бэкенд мапит `surname → lastName`);
  одного `lastName` недостаточно — строка создавалась без имени. Поле
  `deliveryType` пишется прямо в внешний ключ `group_id`, поэтому строка вроде
  `"car"` роняет регистрацию по constraint. По умолчанию поле не отправляется;
  чтобы привязать группу, задайте `FIXTURE_COURIER_GROUP_ID` (UUID из
  `GET /api/admin/groups`).
- **Ресторан.** `restName`, `login`, `password` и `city` обязательны, город
  проверяется по справочнику платформы. Город настраивается через `FIXTURE_CITY`;
  отказ бэкенда движок переводит в подсказку с перечнем недостающих полей.

### 4.8 Ошибочные ответы со статусом 301

Часть ручек (`loginAdmin`, `loginRest`, `regCourier`) сообщает об ошибке через
`e.status = 301`, а не 4xx. Движок считает провалом любой ответ вне 2xx: без
этого `LoginAdmin` возвращал текст ошибки вместо токена, и падение всплывало
позже и не там. Go сам следует за 3xx с заголовком `Location`, так что видимым
здесь 301 остаётся ровно эта ошибочная конвенция.

### 4.9 Требования к стенду

Чтобы прогоны шли без человека:

```
DEBUG=true          # иначе в ответе register не будет debugCode
```

Проверить, что стенд готов:

```bash
curl -s -X POST http://127.0.0.1:3005/api/clients/register \
  -H 'Content-Type: application/json' -d '{"phoneNumber":"+79995550101"}'
# ожидается: {"firstTime":true,"message":"success","debugCode":"4821"}
```

Если `debugCode` в ответе нет — на стенде развёрнута сборка без LOCALIAPP-2343,
либо `DEBUG` не выставлен. Сьют `auth_otp` в этом случае честно падает на
проверке `otp_issued` с объяснением.

## 5. Заказы: контракт и предусловия

### 5.1 Ресторанный заказ собирается из корзины

`POST /api/clients/create-order` не принимает состав заказа. Позиции берутся из
серверной корзины клиента, а тело запроса только описывает, как и куда отдать
заказ:

```json
{
  "rest_id": "…",
  "receiveMethod": "delivery",
  "address_id": "…",
  "payment": { "type": "cash" },
  "source": "lokali_eda"
}
```

`payment` — объект, а не строка; `receiveMethod` обязателен; адрес доставки
передаётся идентификатором сохранённого адреса, а не текстом. Неизвестный
`source` отклоняется (допустимы `lokali_eda` и `crispy_app`).

Чтобы заказ вообще создался, до него нужна целая подготовленная ситуация:

| Шаг | Что делает | Без него |
|-----|------------|----------|
| 1 | Регистрация ресторана с `deliveryEnabled`/`pickupEnabled` | `RECEIVE_METHOD_DISABLED` |
| 2 | `PUT /api/rests/schedule` — 7 дней | `RESTAURANT_CLOSED` |
| 3 | `POST /api/rests/categories` | блюдо не создать |
| 4 | `POST /api/rests/dishes` (`title`, `price`, `category_id`) | нечего заказывать |
| 5 | `POST /api/clients/addresses` | `DELIVERY_ADDRESS_REQUIRED` |
| 6 | `POST /api/cart/items` | `CART_EMPTY` |

Всё это делает `Fixtures.PrepareRestaurantOrder(ctx)`, возвращая `OrderContext`;
`octx.OrderRequest()` даёт готовое валидное тело заказа. Ошибка любого шага
называет сам шаг — стенд может отказать по причинам, не связанным с тестом.

### 5.2 Посылка А→Б

`POST /api/clients/independent-order` адресуется координатами и требует
получателя, тип груза и тип курьера:

```json
{
  "fromLat": 43.3169, "fromLong": 45.6981,
  "toLat": 43.3269,  "toLong": 45.7081,
  "courierType": "bike", "cargoType": "documents",
  "paymentType": "cash",
  "recipientName": "Получатель Тестовый",
  "recipientPhone": "+79991234567"
}
```

Готовое тело даёт `Fixtures.ParcelRequest("")`.

**Рабочее окно.** Платформа принимает посылки только с 10:00 до 23:00. Вне окна
любой заказ отклоняется с `422 OUTSIDE_WORKING_HOURS` — это закрытая платформа,
а не дефект, поэтому сьюты посылок **пропускаются** (`SKIP`), а не падают.
Проверка окна — `Fixtures.ParcelOrderingAvailable(ctx)`.

### 5.3 Ответы, на которые нельзя полагаться

- `POST /api/couriers/change-status` возвращает то обновлённый заказ, то сырой
  результат Sequelize (`[1]`). Движок разбирает тело мягко и не считает `[1]`
  ошибкой; терминальный статус читается обратно через
  `ClientAPI.GetFinalOrder` — из истории, потому что доставленный заказ уже не
  активен.
- Именование полей различается: создание отвечает в snake_case (`order_id`),
  а чтения прогоняют строку через `toCamelCase` (`orderId`). `OrderResponse`
  принимает оба варианта.
- Отмена во время готовки — это `409 CANCEL_NOT_ALLOWED` (конфликт состояния),
  а не 403: заказ принадлежит клиенту, отменить не даёт статус.

### 5.4 Настройка стенда под фикстуры

```
FIXTURE_CITY=Грозный            # город из supportedCities активного тарифа Locali
FIXTURE_LATITUDE=43.3169
FIXTURE_LONGITUDE=45.6981
FIXTURE_COURIER_GROUP_ID=       # пусто = курьер без группы (бэкенд это принимает)
```

Если активного тарифа Locali нет, доставка отклоняется с
`409 LOCALI_DELIVERY_TARIFF_NOT_CONFIGURED` — тариф заводится админкой
(`PUT /api/admin/delivery/locali-tariff`), и его `supportedCities` определяют,
в каком городе фикстуры вообще смогут заказывать.

## 6. Аккаунты: вход по номеру и привязка к прогонам

### 6.1 Вход одним номером

Клиент входит по одноразовому коду, а не по паролю. На стенде с `DEBUG=true`
код возвращается в ответе на запрос, поэтому в «Логин через API» достаточно
ввести номер — движок сам запросит код и войдёт:

```bash
curl -X POST localhost:18080/api/tokens/auth-login \
  -H 'Content-Type: application/json' \
  -d '{"role":"client","phoneNumber":"+79995551010","profileName":"Клиент Иван"}'
```

Поле кода остаётся: если стенд без `DEBUG` или код уже отправлен и действует
пауза в 60 секунд, его вводят вручную — движок скажет об этом текстом ошибки.

Остальные роли входят логином и паролём той же ручкой (`role`: `rest`,
`courier`, `admin`).

### 6.2 Какими аккаунтами идут прогоны

По умолчанию каждый сьют создаёт себе новые аккаунты — прогоны не мешают друг
другу и не зависят от состояния стенда. Вкладка **Хранилище → «Аккаунты для
прогонов»** позволяет указать конкретный профиль на роль.

Это нужно, когда на стенде есть подготовленные вручную данные, которых у
сгенерированной фикстуры не будет: ресторан с настоящим меню, курьер в нужной
группе, клиент с историей заказов.

```bash
# привязать
curl -X POST localhost:18080/api/fixtures/accounts \
  -H 'Content-Type: application/json' \
  -d '{"client":"<profileId>","rest":"<profileId>","courier":"","admin":""}'

# посмотреть текущую привязку
curl localhost:18080/api/fixtures/accounts
```

Пустая строка снимает привязку и возвращает роль к генерации.

Что важно знать:

- **Роль токена проверяется.** Клиентский профиль не привяжется к роли курьера —
  иначе сьюты шли бы под чужой личностью и всё равно зеленели.
- **Курьер отдаёт `courier_id`, а не телефон**: админка назначает заказы по id,
  и привязка без `user_id` в токене отклоняется.
- **Привязка живёт вместе с токенами стенда** — переживает перезапуск, а при
  переключении стенда применяется привязка этого стенда, а не предыдущего.
- **Удаление профиля снимает привязку**, чтобы сьют не остался с токеном,
  которого больше нет в хранилище.
- **У привязанного ресторана** сьют заказывает уже существующее блюдо, а не
  плодит новые на каждый прогон, но расписание выставляет круглосуточным —
  иначе закрытая точка отклонит заказ. Об этом пишется в журнал прогона.

## 7. Два вида проверок

Каталог разделён на две части, и в UI они показаны отдельными секциями.

**Сценарии** — сквозные флоу. Каждый шаг зависит от предыдущего, прогон
останавливается на первом провале: готовить заказ, который не создался, незачем.

**API-проверки ручек** (`category: api`) — контракт одной ручки. Проверки
независимы: одна сломанная ручка не скрывает состояние остальных, поэтому
выполняются все, и набор показывает картину по всей зоне.

| Набор | Что покрывает |
|-------|---------------|
| `api_menu` | категории, блюдо: создание, чтение, редактирование, скрытие, стоп-лист, удаление, валидация |
| `api_modifiers` | модификаторы и группы: создание, правка, лимиты выбора, удаление, изоляция |
| `api_cart` | корзина: добавление, количество, очистка, отказ при пустой корзине |
| `api_wallet` | кошельки курьера и ресторана: баланс, операции, пополнение, изоляция |
| `api_order_status` | гарды смены статуса: принятие заказа, переводы ресторана, отмена, назначение |
| `api_guards` | матрица ролевого доступа по зонам + отсутствие и порча токена |

### 7.1 Статус прогона отражает исход проверок

- есть провалы → `FAILED`;
- провалов нет, но что-то пропущено → `SKIPPED` (сьют выполнен не полностью);
- всё выполнено и пройдено → `PASSED`.

Пропуск — не успех: проверка ничего не доказала. Раньше сьют с одной пройденной
и четырьмя пропущенными проверками показывал «ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ» и зелёный
`PASSED`; теперь баннер говорит «пройдено 1, пропущено 4», а сами проверки
отрисовываются как пропущенные, а не висят в состоянии выполнения.

Аналогично API-набор, где ничего не оборвалось, но три проверки провалились,
теперь отдаёт `FAILED`, а не `PASSED`.
